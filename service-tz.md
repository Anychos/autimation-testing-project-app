# TaskFlow — реализация независимого микросервиса Notification Service

## 1. Роль и основная задача

Ты выступаешь в роли Senior Python Backend Developer и Software Architect.

Необходимо расширить существующий проект TaskFlow, реализовав отдельный микросервис уведомлений с асинхронным межсервисным взаимодействием, собственной базой данных, REST API и локальной отправкой электронной почты.

Проект является учебным полигоном для QA Automation Engineer. Его основное назначение — практическое изучение автоматизации API, UI, интеграционного, контрактного и микросервисного тестирования.

Поэтому при реализации необходимо уделять особое внимание:

- Предсказуемому поведению системы.
- Тестируемости компонентов.
- Документированным контрактам.
- Изоляции данных.
- Воспроизводимости ошибок.
- Возможности тестировать сервисы независимо.
- Возможности имитировать недоступность компонентов инфраструктуры.
- Диагностике межсервисного взаимодействия.

Не ограничивайся написанием плана или примеров кода. Необходимо реализовать рабочий сервис, интеграцию и Docker-инфраструктуру.

## 4. Независимость микросервиса

Notification Service должен находиться в отдельной директории:

`notification-service/`

Он должен иметь собственные:

- pyproject.toml.
- Dockerfile.
- compose.yaml.
- .env.example.
- README.md.
- .dockerignore.
- Миграции базы данных.
- Исходный код.
- Контракты событий.
- Вспомогательные скрипты.
- Минимальные внутренние тесты.

Микросервис должен запускаться без запуска основного backend и frontend TaskFlow.

Запуск из директории notification-service:

```bash
docker compose up -d --build
```

Остановка:

```bash
docker compose down
```

Перезапуск Notification Service не должен приводить к остановке основного TaskFlow.

Остановка TaskFlow не должна приводить к остановке Notification Service.

Не допускай прямого доступа Notification Service к базе данных основного backend.

Обмен данными между сервисами должен осуществляться только через документированные HTTP- и AMQP-контракты.

## 5. Docker-инфраструктура

Создай отдельный Docker Compose со следующими компонентами.

| Docker service | Назначение |
|---|---|
| notification-api | FastAPI-приложение |
| notification-worker | Обработчик событий и отправитель писем |
| notification-db | PostgreSQL |
| notification-migrations | Одноразовый запуск миграций |
| rabbitmq | Брокер сообщений |
| mailpit | Локальный SMTP-сервер и почтовый интерфейс |

API и Worker должны использовать один Docker-образ приложения, но запускаться разными командами и в разных контейнерах.

API-контейнер должен отвечать за HTTP-запросы.

Worker должен отвечать за:

- Подключение к RabbitMQ.
- Получение событий.
- Валидацию событий.
- Создание уведомлений.
- Планирование и обработку отправки писем.
- Повторные попытки.
- Обработку ошибок.

Worker должен запускаться отдельно от API, чтобы можно было остановить обработку событий, сохранив доступность REST API.

### 5.1. Порты

Предпочтительная конфигурация:

| Компонент | Host port | Container port |
|---|---:|---:|
| Notification API | 8001 | 8000 |
| PostgreSQL | 5433 | 5432 |
| RabbitMQ AMQP | 5672 | 5672 |
| RabbitMQ Management | 15672 | 15672 |
| Mailpit SMTP | 1025 | 1025 |
| Mailpit Web/API | 8025 | 8025 |

Все опубликованные порты должны быть доступны только локально через 127.0.0.1.

Предусмотри возможность изменить host-порты через переменные окружения.

Проверь конфликты с существующим Docker Compose TaskFlow.

### 5.2. Docker-сети

Notification Service должен иметь собственную внутреннюю сеть.

Для взаимодействия с основным TaskFlow создай общую внешнюю Docker-сеть:

```bash
docker network create taskflow-network
```

Подключи к ней только компоненты, которым необходимо межсервисное взаимодействие.

В частности:

- TaskFlow Backend.
- Notification API.
- RabbitMQ.

PostgreSQL и Mailpit не требуется подключать к общей межсервисной сети.

Добавь скрипт или документированную команду для идемпотентного создания общей сети перед запуском.

Оба Compose-проекта должны использовать эту сеть независимо друг от друга.

Внутри Docker обращайся к сервисам по сетевым именам, а не через localhost.

Не подключай сервисы к host network.

### 5.3. Надёжность Docker-инфраструктуры

Реализуй:

- Healthchecks.
- Корректный порядок запуска зависимостей.
- Ожидание готовности PostgreSQL и RabbitMQ.
- Автоматическое переподключение Worker.
- Именованные Docker volumes.
- Сохранение данных после перезапуска.
- Сохранение данных RabbitMQ.
- Персистентное хранение писем Mailpit.
- Корректную обработку SIGTERM.
- Graceful shutdown.
- Отдельный запуск миграций перед API и Worker.

Запуск контейнера не должен считаться успешным исключительно по факту запуска процесса.

## 6. Основная функциональность

Notification Service должен создавать уведомления на основании событий, получаемых от TaskFlow.

Поддерживаемые каналы:

1. IN_APP — уведомление внутри приложения.
2. EMAIL — электронное письмо через локальный SMTP.

Один входящий бизнес-event должен создавать одно логическое уведомление с независимым состоянием доставки по каждому необходимому каналу.

### 6.1. Поддерживаемые события

| Event type | Условие возникновения | IN_APP | EMAIL |
|---|---|---|---|
| user.registered | Успешная регистрация пользователя | Да | Да |
| task.created | Создание задачи | Да | Да |
| task.updated | Изменение данных задачи | Да | Нет |
| task.completed | Переход статуса задачи в done | Да | Да |
| task.deleted | Удаление задачи | Да | Нет |

Если задача изменяется со статуса todo или in_progress на done, публикуй task.completed вместо дополнительного task.updated для этой же операции.

Повторное сохранение задачи со статусом done не должно создавать новое уведомление о завершении задачи.

Запрос, не изменивший данные задачи, не должен создавать task.updated.

Неуспешные операции, включая ошибки авторизации, валидации и отсутствующие сущности, не должны публиковать бизнес-события.

Авторизация пользователя не должна отправлять письмо при каждом входе.

Дедлайны, просроченные задачи и пользовательские настройки каналов уведомлений оставить для следующей версии.

## 7. Контракт событий

Все события должны иметь единый envelope.

Пример события создания задачи:

```json
{
  "event_id": "3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "event_type": "task.created",
  "schema_version": 1,
  "occurred_at": "2026-11-27T10:00:00Z",
  "source": "taskflow-backend",
  "correlation_id": "94af3be7-5702-4b7a-8db7-a5b18d598163",
  "user_id": "e3c43b8c-5702-4b7a-8db7-a5b18d598164",
  "payload": {
    "task_id": "d8c43b8c-5702-4b7a-8db7-a5b18d598165",
    "title": "Learn Python",
    "status": "todo",
    "recipient_email": "test@example.test"
  }
}
```

### 7.1. Общие требования

- event_id — уникальный UUID бизнес-события.
- event_type — поддерживаемый тип события.
- schema_version — версия контракта.
- occurred_at — UTC datetime с timezone.
- source — идентификатор источника события.
- correlation_id — идентификатор для сквозной диагностики.
- user_id — идентификатор получателя уведомления.
- payload — данные конкретного события.

Для каждого event_type реализуй отдельную Pydantic-схему payload.

Используй discriminated union или другой явно типизированный механизм выбора схемы.

Не допускай передачи:

- Паролей.
- Access tokens.
- Refresh tokens.
- Cookies.
- Сессионных данных.
- Других секретов.

Получатель письма должен определяться основным backend на основании авторизованного пользователя, а не произвольного email из запроса на создание задачи.

Значения бизнес-полей должны соответствовать фактическим ограничениям существующего TaskFlow.

Для событий версии 1 сформируй документированные JSON Schema и примеры валидных и невалидных сообщений.

Сохраняй обратную совместимость контракта в рамках одной версии.

## 8. RabbitMQ

Настрой topic exchange:

`taskflow.events`

Routing keys:

- user.registered
- task.created
- task.updated
- task.completed
- task.deleted

Основная очередь:

`notification.events`

Retry-очереди:

- notification.events.retry.5s
- notification.events.retry.15s
- notification.events.retry.30s

Dead Letter Exchange:

`notification.dlx`

Dead Letter Queue:

`notification.events.dlq`

Топология должна автоматически создаваться при запуске инфраструктуры и не требовать ручного создания очередей через RabbitMQ Management.

Конфигурация Producer и Consumer должна использовать совместимые параметры exchange, queue и bindings.

### 8.1. Producer

В основном TaskFlow Backend реализуй отдельный компонент публикации событий.

Требования:

- Durable exchange и очереди.
- Persistent messages.
- Publisher confirms.
- Обработка unroutable messages.
- Таймауты.
- Переподключение.
- Структурированное логирование.
- Сохранение correlation_id.
- Повторное использование исходного event_id при повторной публикации.

### 8.2. Consumer

Notification Worker должен:

1. Получить сообщение.
2. Десериализовать JSON.
3. Валидировать envelope.
4. Валидировать payload.
5. Проверить event_id на повторную обработку.
6. В одной транзакции создать уведомление и необходимые записи доставки.
7. Зафиксировать изменения в PostgreSQL.
8. Подтвердить обработку сообщения через manual ACK.

Не использовать auto_ack=True.

Если запись в БД завершилась ошибкой, сообщение нельзя считать успешно обработанным.

Сетевой сбой или завершение Worker до ACK не должны приводить к потере события при штатной повторной доставке брокером.

### 8.3. Retry

Временные ошибки обработки должны приводить к ограниченному числу повторных попыток.

Начальные интервалы:

- 5 секунд.
- 15 секунд.
- 30 секунд.

Интервалы и количество попыток должны быть конфигурируемыми.

Не реализовывай бесконечный немедленный requeue для ошибок обработки.

При перемещении события в retry-очередь или DLQ используй подтверждённую публикацию до ACK исходного сообщения.

Сохраняй event_id, correlation_id и информацию о попытках.

Если повторную публикацию не удалось подтвердить, исходное сообщение не должно быть потеряно.

### 8.4. Dead Letter Queue

В DLQ должны попадать:

- Некорректный JSON.
- Неподдерживаемая версия контракта.
- Неподдерживаемый тип события.
- Сообщения с отсутствующими обязательными полями.
- Сообщения, исчерпавшие лимит повторных попыток обработки.

Добавляй доступную для диагностики причину ошибки и исходные метаданные события.

Некорректное сообщение не должно останавливать Worker.

После обработки невалидного сообщения Worker должен продолжать принимать корректные события.

## 9. Transactional Outbox в основном backend

Реализуй надёжную публикацию бизнес-событий через паттерн Transactional Outbox.

Не связывай успешность регистрации или CRUD-операций с текущей доступностью RabbitMQ или Notification Service.

При включённой интеграции запись бизнес-сущности и запись соответствующего outbox-события должны выполняться в одной транзакции основной базы данных.

Добавь отдельную таблицу outbox_events.

Предлагаемые поля:

- id.
- event_type.
- payload.
- correlation_id.
- status.
- attempt_count.
- created_at.
- published_at.
- next_attempt_at.
- last_error.

Реализуй Outbox Publisher в основном проекте.

Он может запускаться отдельным Docker-контейнером на базе существующего backend-образа.

Порядок работы:

1. Найти неопубликованные события.
2. Отправить событие в RabbitMQ.
3. Получить подтверждение публикации.
4. Отметить событие опубликованным.
5. При ошибке сохранить диагностическую информацию и время следующей попытки.

При недоступности брокера события должны оставаться в outbox.

После восстановления RabbitMQ накопленные события должны автоматически публиковаться.

Предусмотри безопасную обработку конкурентными экземплярами Publisher.

Учитывай возможность повторной доставки одного события при сбое между подтверждением RabbitMQ и обновлением outbox.

Не заявляй гарантию exactly-once delivery.

Используй at-least-once delivery совместно с идемпотентным Consumer.

Добавь конфигурацию NOTIFICATIONS_ENABLED, позволяющую запускать существующий TaskFlow без включённой интеграции уведомлений.

## 10. PostgreSQL микросервиса

Notification Service должен иметь собственную базу данных.

Не используй общие ORM-модели основного backend.

### 10.1. Таблица notifications

Поля:

| Поле | Тип |
|---|---|
| id | UUID |
| event_id | UUID, unique |
| user_id | UUID |
| event_type | String |
| task_id | UUID, nullable |
| title | String |
| message | Text |
| is_read | Boolean |
| read_at | Datetime, nullable |
| created_at | Datetime |
| event_occurred_at | Datetime |
| correlation_id | UUID |

Значения по умолчанию:

- is_read = false.
- read_at = null.
- created_at = текущее UTC-время.

Добавь индексы по:

- user_id.
- event_id.
- task_id.
- event_type.
- created_at.
- is_read.

### 10.2. Таблица notification_deliveries

Поля:

- id.
- notification_id.
- channel.
- recipient.
- status.
- attempt_count.
- next_attempt_at.
- last_error.
- created_at.
- sent_at.
- message_id.

Каналы:

- IN_APP.
- EMAIL.

Статусы:

- PENDING.
- PROCESSING.
- RETRYING.
- SENT.
- FAILED.

Для IN_APP уведомление считается доставленным после успешного сохранения в базе.

Для EMAIL статус SENT устанавливается только после успешного принятия сообщения SMTP-сервером.

Добавь уникальное ограничение на комбинацию notification_id и channel.

### 10.3. Идемпотентность

Повторное получение события с одинаковым event_id не должно создавать повторные записи notifications или notification_deliveries.

Реализуй защиту на уровне БД, а не только предварительной проверкой SELECT.

Обеспечь корректное поведение при конкурентной обработке событий.

Повторное событие с тем же event_id, но отличающимся содержимым должно диагностироваться как конфликт контракта и не изменять исходное уведомление.

## 11. Локальная электронная почта

Используй официальный Docker-образ Mailpit.

SMTP-конфигурация:

```env
SMTP_HOST=mailpit
SMTP_PORT=1025
SMTP_FROM_EMAIL=notifications@taskflow.test
SMTP_FROM_NAME=TaskFlow
SMTP_USE_TLS=false
SMTP_USE_SSL=false
SMTP_TIMEOUT=5
```

Web-интерфейс:

`http://localhost:8025`

REST API:

`http://localhost:8025/api/v1/`

Вся почта должна оставаться внутри локальной среды.

Не настраивай внешние SMTP relay, пересылку писем, Gmail, SendGrid и аналогичные сервисы.

Для отправки уведомлений используй SMTP-протокол, а не прямое создание сообщений через REST API Mailpit.

REST API Mailpit предназначен для просмотра и последующей автоматизации проверки отправленных писем.

### 11.1. Шаблоны писем

Создай отдельные HTML- и plain-text-шаблоны.

Язык писем — английский, в соответствии с интерфейсом TaskFlow.

Приветственное письмо:

- Subject: Welcome to TaskFlow!
- Body: Your account has been successfully created.

Создание задачи:

- Subject: New task created
- Body: Your task "{task_title}" has been created successfully.

Завершение задачи:

- Subject: Task completed
- Body: Congratulations! You have completed "{task_title}".

Письма должны содержать:

- Название TaskFlow.
- Заголовок.
- Текст уведомления.
- Данные соответствующей задачи, если применимо.
- Дату события.
- HTML- и текстовую части.

Экранируй пользовательский текст в HTML-шаблонах.

Не допускай внедрения пользовательских данных в SMTP-заголовки без валидации.

### 11.2. Диагностические заголовки

Добавляй в электронные письма:

- Message-ID.
- X-Event-ID.
- X-Correlation-ID.
- X-Notification-ID.
- X-Task-ID, если применимо.

Используй стабильный Message-ID для повторных попыток одной логической доставки.

Эти заголовки необходимы для поиска конкретного письма в автоматизированных тестах.

### 11.3. Недоступность SMTP

Отправка электронной почты не должна блокировать создание IN_APP-уведомления.

Если Mailpit недоступен:

1. Уведомление должно быть создано в PostgreSQL.
2. Запись EMAIL-доставки должна остаться в очереди на отправку.
3. Worker должен выполнить ограниченное количество повторных попыток.
4. После восстановления SMTP письмо должно быть отправлено, если лимит попыток ещё не исчерпан.
5. После исчерпания лимита статус доставки должен стать FAILED.

Реализуй обработку email-доставок как отдельный цикл Worker с использованием сохранённых в БД записей.

Не блокируй RabbitMQ Consumer длительным ожиданием SMTP.

Предусмотри восстановление зависших PROCESSING-доставок после аварийного завершения Worker.

Не создавай новое логическое уведомление при повторной попытке отправки письма.

Учитывай, что SMTP не гарантирует exactly-once: при аварии после принятия письма SMTP-сервером, но до обновления БД, физический дубликат письма теоретически возможен. Документируй это ограничение.

## 13. Авторизация и безопасность

Изучи существующий механизм авторизации TaskFlow.

Не создавай вторую независимую систему регистрации пользователей внутри Notification Service.

Предпочтительная архитектура для текущего MVP:

Frontend обращается к основному TaskFlow Backend.

TaskFlow Backend:

1. Проверяет существующую пользовательскую сессию.
2. Определяет user_id.
3. Выполняет HTTP-запрос к Notification API.
4. Передаёт подтверждённый user_id и внутренний service-to-service credential.

Notification API проверяет внутренний credential и ограничивает все операции соответствующим user_id.

Не доверяй произвольному X-User-ID, пришедшему непосредственно от frontend.

Внутренний credential должен храниться только в переменных окружения backend-сервисов.

Для самостоятельного локального API-тестирования документируй использование service credential и тестового user_id без запуска основного TaskFlow.

Каждый пользователь должен иметь доступ только к своим уведомлениям.

Получение, изменение и удаление чужого уведомления должны возвращать 404, чтобы не раскрывать существование чужой сущности.

Если существующий проект использует подходящий механизм проверяемых JWT, допускается альтернативная интеграция. Обоснуй выбранное решение в README.

- Worker продолжает обрабатывать другие события.

## 24. Definition of Done

Работа считается завершённой, если:

- [ ] Notification Service запускается отдельно от TaskFlow.
- [ ] Все необходимые компоненты работают локально в Docker.
- [ ] RabbitMQ Management доступен.
- [ ] Mailpit Web UI и REST API доступны.
- [ ] Notification API и Swagger доступны.
- [ ] PostgreSQL и миграции работают.
- [ ] Регистрация создаёт приветственное уведомление и письмо.
- [ ] Создание задачи создаёт уведомление и письмо.
- [ ] Изменение задачи создаёт уведомление.
- [ ] Завершение задачи создаёт уведомление и письмо.
- [ ] Удаление задачи создаёт уведомление.
- [ ] Невалидные операции не публикуют бизнес-события.
- [ ] Повторное событие не создаёт дубликат логического уведомления.
- [ ] Некорректные события попадают в DLQ.
- [ ] Retry работает и имеет ограничение количества попыток.
- [ ] Недоступность RabbitMQ не блокирует основные операции TaskFlow.
- [ ] События из Outbox доставляются после восстановления брокера.
- [ ] Недоступность Mailpit не блокирует IN_APP-уведомления.
- [ ] Worker восстанавливает подключения после перезапуска зависимостей.
- [ ] Уведомления отображаются в Dashboard.
- [ ] Пользователь не имеет доступа к чужим уведомлениям.
- [ ] Существующая функциональность TaskFlow сохранена.
- [ ] Контракты событий документированы.
- [ ] CLI позволяет публиковать тестовые события независимо.
- [ ] README содержит воспроизводимые инструкции.
- [ ] Все реализованные сценарии, которые возможно проверить в текущем окружении, фактически проверены.
